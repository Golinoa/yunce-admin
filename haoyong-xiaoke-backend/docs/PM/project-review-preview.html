关键短板

真正卡点

机构主体和租户隔离没有完全立住，校长视角和机构经营视角还不够强。

高风险

规模化障碍

如果直接按标准 SaaS 推 1000 家机构，后续会放大数据隔离、角色边界和运营承接问题。

核心判断

高置信 当前状态

不是没有做出来，而是边界没收住

  • 后端已经覆盖认证、学生、班级、排课、课包、消课、请假、通知、统计、反馈等主链路。
  • 小程序已有正式产品感，不只是原型页。
  • 后台管理系统已经具备运营配置和运营执行能力。
高优先级 结构问题

离 1000 家机构还差一层 SaaS 骨架

  • 机构主体、校长角色、校区、教师、学生之间的归属关系还不够清晰。
  • 前端还有 Mock 残留和令牌续期问题。
  • 后台能配活动，但小程序承接页不完整，转化闭环不够顺。

三端现状

后端

业务能力最完整

  • 核心教务业务已成型。
  • 管理后台接口覆盖运营动作。
  • 适合先支撑 1-10 家试点机构。
小程序

体验好于联调

  • 页面完成度高。
  • 部分服务仍依赖 Mock。
  • 401 后未自动刷新登录态。
运营后台

方向是对的

  • 会员管理、激活码、邀请积分、反馈处理都已具备雏形。
  • 可支撑“开通-使用-续费-反馈”基础运营闭环。
  • 但活动页前台承接不完整。

当前最适合的产品策略

方案 适用场景 优点 缺点 建议
方案 A：继续全量推进 想同时做校长、教师、家长、运营活动全覆盖 功能面看起来更大 联调周期长，MVP 不容易真正上线 不建议当前采用
方案 B：聚焦机构开通 + 教师教务 + 后台运营 想尽快拿试点机构，验证可付费性 离成交最近，产品边界更容易收口 家长端和高级玩法需要延后 推荐
方案 C：先做单机构版本 团队小、时间紧，先要案例和现金流 最快落地，最快签首批客户 后续仍要补 SaaS 化改造 可作为 Plan B

两周收口建议

  1. P0 - 明确产品边界： 先决定首版是“单机构试点工具”还是“标准 SaaS”。这一步不定，后面所有需求都会继续发散。
  2. P0 - 修上线阻塞项： 优先处理 401 自动续期、首页运营接口对齐、Teacher Service 去 Mock、活动承接页注册。
  3. P0 - 砍掉非成交主链路： 首版只保留校长开通、教师日常教务、会员续费、反馈处理、基础首页运营位。
  4. P1 - 补机构主体设计： 明确 institution / principal / campus / teacher / student 的归属关系，至少先形成数据模型方案。
  5. P1 - 搭基础运营 SOP： 建立激活码开通、7 天使用辅导、到期续费提醒、反馈回访的标准流程。

高风险清单

风险 1

多租户与机构隔离不足

现阶段更像单库业务集合，不是标准机构级 SaaS。规模化后会直接影响数据隔离和权限正确性。

风险 2

前端联调未完全收口

真实接口未全接、登录态续期缺失、部分服务仍有 Mock，会直接影响试点机构第一印象。

风险 3

运营有后台，无前台承接闭环

后台已具备活动与会员运营能力，但前台活动详情、邀请、续费承接页不完整，影响转化。

待验证

团队资源未知

如果团队不超过 2 人，建议立刻缩小首版范围，不要同时推进家长端深化和复杂增长玩法。

建议的北极星指标

试点机构开通数

衡量销售和开通能力是否跑通。

7 日活跃机构数

衡量机构是否真正开始使用，不只是注册。

到期续费率

衡量会员和激活码运营是否形成价值闭环。

待确认问题

1. 你首批目标是 1-10 家试点机构，还是直接开放公开注册？
2. 你是否接受首版弱化家长端，把资源集中在校长 / 教师主链路？
3. 你更倾向会员订阅、激活码，还是按机构年费收费？
4. 当前团队人数和前后端投入比例是多少？
5. 你希望我下一步继续输出“2 周收口排期表”，还是“商业化与运营方案”？
