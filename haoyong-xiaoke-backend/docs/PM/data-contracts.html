核心数据约定

这份文档不是数据库设计大全，而是当前开发必须遵守的业务数据口径。 目的只有一个：让你在 1 人开发时，不会因为角色、机构、邀请码、会员状态理解不一致而返工。

先说结论

当前最重要的约定有 5 条：`免费版先上线`、`激活码绑定机构`、`教师只能通过临时校区邀请码加入`、`激活后先创建机构`、`会员是高级功能开关而不是基础使用门槛`。

免费版可用

首版所有机构都可免费使用基础功能，会员只影响高级功能。

核心对象约定

对象 业务定义 当前现状 本版开发口径 风险提示
机构 整个教培机构的主体，是会员、激活码、校区、教师、数据归属的根节点。 数据库中尚未看到明确的 Institution 模型，当前更多依赖 Profile / Teacher / Campus 的组合表达。 前端和接口层必须先按“机构主体存在”来设计，不要继续用“老师个人组织名”代替机构。 这是当前最重要的结构缺口，[待验证] 可先用轻量表或临时关联字段落地。
校长 机构管理员，负责创建机构、创建校区、邀请教师、查看机构级状态。 已有 PRINCIPAL 角色。 校长首次进入后，未创建机构就强制进入“创建机构”页。 不要再让校长首次进入直接落首页。
校区 机构下的运营单元，可有一个或多个。 已有 Campus 模型和 CRUD 接口。 校区一定归属于机构，不允许脱离机构独立存在。 当前 Schema 未直接展示机构外键，后续需补齐。
教师 加入某机构某校区后才能执行教务动作。 已有 Teacher 模型，关联 Profile、Campus。 教师加入成功前，不允许进入完整教务页。 当前前端教师服务仍全 mock，需要先按新加入链路改造。
学生 由教师创建和维护的学员实体。 已有 Student 模型和完整路由基础。 学生继续作为教师侧管理对象，不在本版扩大到校长侧全局运营视角。 先保证教师侧真实闭环可用。
激活码 机构级会员或高级能力开关，不是基础使用门槛。 后台已有激活码与会员相关模型和管理能力。 激活码绑定机构，用于解锁高级功能或会员权益。 不要再把“是否激活”当作“是否可用”的前置门槛。
会员状态 区分免费版和会员版的产品状态。 已有 Membership 相关模型。 本版至少要有 `FREE` 和 `MEMBER` 两层状态。 会员页可以简化，但状态语义必须统一。
教师邀请码 校长为教师生成的短时有效加入凭证。 旧有 inviteCode 语义存在，但不完全等于“校区临时邀请码”。 必须支持 30 分钟 / 1 小时 / 3 小时 / 12 小时有效期。 旧邀请码语义可能混淆学生邀请、教师邀请和绑定码，需要拆开命名。

前端状态约定

状态 用户角色 触发条件 应进入页面 禁止进入的页面
UNAUTHENTICATED 全部 未登录 登录 / 注册 首页、教务页、机构页
PRINCIPAL_NO_ORG 校长 已登录但未创建机构 创建机构页 首页、教师管理、校区管理
PRINCIPAL_NO_CAMPUS 校长 已创建机构但无校区 创建校区页 教师邀请、教务大盘
TEACHER_UNBOUND 教师 已登录但未绑定校区 输入邀请码页 学员、班级、消课
READY 校长 / 教师 已满足角色前置条件 首页 / 工作台 无

命名约定

建议统一使用

建议命名

  • 机构：`organization` 或 `institution` 二选一后统一
  • 校区：`campus`
  • 教师临时邀请码：`campusInviteCode` 或 `teacherInviteCode`
  • 免费版状态：`FREE`
  • 会员版状态：`MEMBER`
避免继续混用

避免命名

  • 不要把机构名继续塞进 `organizationName` 的展示字段里冒充真实实体
  • 不要把教师邀请码、学生邀请码、邀请积分邀请码共用一套语义
  • 不要再把“未激活”作为免费用户状态文案

当前执行建议

1. 开发前先把“机构”对象单独立起来，不要求一步做到完美，但要先有明确根节点。
2. 教师加入链路一定要和“校区临时邀请码”绑定，不要沿用旧的宽泛 inviteCode 语义。
3. 前端路由守卫要完全按这份状态约定执行。
4. 所有页面文案都把“未激活用户”改成“免费版用户”。
5. 这份文档开发时应与 `api-alignment.html` 一起使用。
