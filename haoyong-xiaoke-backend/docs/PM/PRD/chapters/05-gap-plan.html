05 查漏补缺与分步完成

本章把前 4 章的结论转化成执行规划：哪些是当前真正阻塞 MVP 的缺口，哪些可以复用现有页面，哪些需要新建 spec，哪些必须明确延后。

1. 已有能力 vs 缺失能力

模块 当前已有 当前缺失 判断
登录与注册 页面与基础守卫已存在 校长首链路仍未完全按“微信登录 -> 选校长 -> 填机构名 -> 自动建主校区 -> 首页”收口 P0
首页工作台 金刚区、通知、内容卡片、常用业务入口已存在 新用户首次进入前置流程不足 P1
校长组织初始化 角色信息页已有机构名称输入，校区设置已有后续管理能力 首链路应收缩为只填机构名称，并补“自动创建默认主校区”规则 P0
教师加入 产品规则已明确 教师输入邀请码独立主流程 P0
学员管理 列表、详情、表单、接口分支、课包初始化都相对完整 需要和新的组织状态链路打通 优先复用

2. 分步完成建议

第一步：收口校长首链路
  - 登录状态检测
  - 微信一键登录
  - 身份选择
  - 校长角色信息页只保留机构名称
  - 自动创建默认主校区

第二步：补教师加入入口
  - 教师邀请码页
  - 教师输入邀请码页

第三步：打通真实业务
  - 学员列表
  - 学员新增
  - 学员详情

第四步：补收口
  - 首页入口文案
  - 免费版/会员版状态说明
  - 异常提示与返回路径

3. 推荐 spec 拆分

前端 spec

建议拆 6 份

登录态与状态机、校长角色信息页、默认主校区自动创建联动、教师邀请码页、教师加入页、学员新增链路。

后端 spec

建议拆 5 份

认证口径、机构主体、默认主校区自动创建规则、教师临时邀请码、教师绑定与学员主链路接口。

4. 风险记录

高风险

校长首链路过长

如果继续把“手工创建校区”放在首链路里，会直接拉长注册完成路径。

高风险

邀请码语义混用

教师邀请码、学生邀请码、邀请积分邀请码不能继续混用。

中风险

组织主体未立住

如果机构主体不明确，后续会员、激活码、权限都会返工。

5. 当前版本边界

当前版本完成标准不是“功能很多”，而是“一个新机构能顺利走完第一次使用”。
所以本版做：状态机、校长角色信息收口、默认主校区自动创建、教师加入、学员新增闭环。
本版不做：积分、广告、任务中心、家长端深化、复杂运营能力。

6. 本章结论

1. 现有前端不是重做，而是收口。
2. 当前最值得复用的是学员链路。
3. 当前最需要纠正的是校长初始化链路，不是继续假设一个手工建校区页。
4. 后续如果你认可，这套 PRD 可以继续扩成更细的页面级章节，但已经足够支持当前一轮 spec 编写。
