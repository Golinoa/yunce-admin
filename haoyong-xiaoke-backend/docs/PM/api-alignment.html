PM 总览首页 开发任务拆解 问题记录

接口对齐清单

这份文档的目标不是列全量接口，而是列出当前 MVP 闭环真正要对齐的接口。 你开发时优先按这里逐项打通。能直接支撑“注册 -> 创建机构 -> 创建校区 -> 教师加入 -> 首个教务动作”的接口，才是当前 P0。

对齐原则

当前判断标准只有 3 个：前端是否已有调用、后端是否已有真实接口、两边是否已经同口径联调。没有联调就不算完成。

P0

必须打通

认证、机构创建、校区创建、教师加入、首个教务动作。

P1

可延后收口

首页运营位、会员状态、通知设置、工资模型等。

P2

后续再接

邀请积分、签到积分、积分兑换会员卡等增长能力。

P0 接口对齐表

模块 前端现状 后端现状 联调状态 问题 建议动作
登录 / 注册 auth.ts 中微信登录、手机号登录、会话读取已接真实后端；账号密码、邮箱验证码、分步注册仍返回“暂未接通”。 /auth/login、/wechat-login、/phone-login、/register、/me、/refresh 已存在。 部分已通 真实后端与前端当前登录口径不一致，分步注册还未对上。 先锁定首版登录方式：微信 + 手机号；账号密码和邮箱相关逻辑先隐藏或降级。
邀请码校验 validateInviteCode() 已接 /auth/invite-code/:code/validate；verifyCampusCode() 和 verifyStudentCode() 仍是 mock-only。 只有“邀请校验”真实接口存在；校区邀请码专用接口当前未见明确实现。 未对齐 你已经改成“教师通过临时校区邀请码加入”，但接口还没有完整匹配这个规则。 新增或重构“校区临时邀请码生成 + 校验 + 消费”接口，再同步前端加入页。
校区管理 campusService 的列表、详情、增删改、设主校区仍主要走 mock。 /campuses 已有真实列表、详情、创建、更新、设主校区、删除接口。 未对齐 后端已具备，但前端还没切真实接口。 优先把创建机构后的首个校区流程切到真实接口，不必一次性全部切完。
教师管理 / 教师加入 teacherService 当前完全基于 mock 数据。 /teachers 真实接口较完整，但当前更偏教师管理与薪资，不是“临时邀请码加入”模型。 未对齐 前端无真实联调；后端也尚未完全按你最新的产品规则建模。 先补教师加入专用接口，不要先接薪资、扣款、发薪等次要接口。
学生主链路 studentService 已有大量真实接口分支，但仍混用 mock。 /students 已有列表、详情、创建、更新、绑定家长、课时统计等接口。 可打通 能力很多，但需要选一条真实主链路先验证，而不是全量切换。 建议先打通“教师创建学生 -> 查看详情”，再决定是否继续接班级和消课。

当前联调结论

1. 后端能力比前端真实联调成熟得多。
2. 当前真正应该优先对齐的不是“更多接口”，而是“更少但能闭环的接口”。
3. 第一批只要打通：登录、会话、机构创建、校区创建、教师加入、学生创建。
4. 在这之前，所有工资、通知、活动、积分接口都不要抢资源。
5. 你开始开发时，这份文档应与 `dev-task-breakdown.html` 一起打开使用。
