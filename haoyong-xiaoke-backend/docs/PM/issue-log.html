问题记录

这份记录只收纳“会影响 MVP 上线、联调效率、数据安全和后续产品骨架”的问题。 我已经剔除了低价值的样式问题和泛泛而谈的建议，保留的是当前版本真正需要处理的阻塞项。

问题分层

先看严重度，再决定行动顺序。当前建议是：先清 P0，P1 不阻塞上线，P2 进入后续规划。

P0

必须立即处理

不解决就会直接影响注册、登录、机构入驻或首个教务动作。

P1

不阻塞上线

会影响真实体验、效率或长期结构，但可以在 MVP 跑通后继续修。

P2

后续优化

当前版本不处理，统一放到后续版本或开源工具补位阶段。

完整问题清单

优先级 问题 当前现象 影响 建议动作 证据
P0 登录态刷新闭环未收口 小程序端仍以本地 token 检查和被动刷新为主，401 相关处理不够完整。 真实用户登录后可能掉线或需要重复登录，直接影响首批试用印象。 先统一 access token 失效后的 refresh 策略，再清理登录态和路由守卫逻辑。 src/utils/route-guard.tsx
P0 机构主实体与教师加入链路未打穿 后端已有校长、校区、教师相关模块，但当前产品规则刚刚确定为“机构 -> 校区 -> 邀请教师”，实现还未统一。 MVP 无法形成机构级闭环，校长注册后不一定知道下一步做什么。 优先做创建机构、创建校区、临时邀请码、教师加入 4 个页面和对应接口约束。 src/routes/index.ts / src/campus
P0 免费版与会员版状态语义尚未统一 业务已经改成“免费版先上线”，但已有文案和部分逻辑仍沿用“未激活”的旧语义。 产品语言不一致，会让用户误解自己不能使用基础功能。 前台统一改为“免费版 / 会员版 / 机构已激活高级能力”三层状态描述。 mvp-launch-checklist.html
P1 小程序端 Mock 残留较多 学生、课程、排课、认证等模块中存在大量 USE_MOCK 分支。 真实联调阶段很难判断问题来自接口还是本地假数据。 先只清理主链路所涉及模块，不要追求一次性把全项目 Mock 清空。 src/services/student.ts / src/services/auth.ts
P1 首页运营接口路径与前后台承接未完全对齐 首页运营位已接入真实接口尝试，但活动、邀请、会员承接页还未完整补齐。 后台配置能力无法顺畅转化为前台运营闭环。 本版先不强求闭环，只保留必要承接；运营体系后续补完。 src/services/home.ts
P1 校长视角和机构数据隔离仍偏弱 后端具备 PRINCIPAL 角色和校区数据，但机构级归属骨架仍需继续加强。 现在不一定阻塞上线，但后续规模化会影响数据安全和权限边界。 先保证 MVP 能用，二期再补更标准的机构实体与租户隔离。 src/auth/auth.service.ts
P2 签到积分、邀请积分、积分兑换会员卡未进入执行闭环 后端已有积分和邀请规则基础，但产品已决定不让它们阻塞首版上线。 当前不影响 MVP 上线，但会影响后续增长节奏。 先保留规则设计和后台基础，二期再补小程序承接和运营中台查看。 src/admin/admin.routes.ts
P2 家长端能力与当前版本主线不一致 代码里保留了家长端相关流程和页面，但你已经决定当前版本弱化家长端。 如果继续扩展会持续分散前端时间。 保持兼容，不再投入新需求，首页和导航不要继续放大家长端入口。 src/pages/profile/index.tsx

当前建议的修复顺序

1. 先修认证和状态机，保证用户不掉线。
2. 再做机构创建、校区创建、邀请码、教师加入。
3. 然后选一条教务真实主链路打穿。
4. 最后才补前台运营承接、会员状态和后续增长入口。
5. 所有积分和广告变现相关内容当前只记账，不进入本周开发主线。
