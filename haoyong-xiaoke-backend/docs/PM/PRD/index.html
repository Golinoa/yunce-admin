松果助教 MVP PRD 门户

这套文档不是“功能清单”，而是面向开发、联调、验收的交互型 PRD。每个核心章节都会尽量回答 4 个问题：用户从哪里进入、点击什么、进入哪个页面、填写什么信息、调用哪个后端接口提交。 页面之间的关系将用 ASCII 与 Mermaid 两种形式同时展示。

版本目标 完成 MVP 闭环
主角色 校长 / 教师
业务原则 免费版先上线
阅读方式 多文档导航

章节地图

我把 PRD 拆成“核心章节 + 页面级 PRD”两层，而不是堆成一个超长文档。这样更适合你逐章 review，也更适合后面继续补充。

01

总览与范围

固定版本目标、角色范围、产品原则、信息架构与本版边界。

 02

导航与状态机

梳理当前页面结构、路由守卫、角色状态跳转和主路径入口。

 03

校长主链路

从校长首次进入开始，梳理机构、校区、邀请教师等核心流程。

 04

教师与学员链路

重点写清学员列表、添加学员、详情、分班和接口调用。

 05

查漏补缺与分步完成

把当前缺口、风险、优先级和建议开发顺序收口成行动计划。

 06

校长机构信息页

定义校长在注册流程中只填写机构名称的最小表单，以及提交后的组织创建逻辑。

 07

默认主校区自动创建规则

明确默认主校区由系统自动生成，而不是让校长在首链路手工填写校区信息。

 08

教师邀请码与绑定页

拆分校长发码和教师绑定两端页面，并明确临时邀请码与教师静态邀请码的差异。

 09

消课记录状态矩阵

沉淀个人消课、补课、取消、班级三角色展示和课包剩余课时三态的统一规则。

这套 PRD 的优缺点

优点

更适合开发执行

按链路和页面拆分，能直接支持前后端写 spec 和联调，不会停留在抽象需求层。

代价

篇幅会更长

因为会写到页面动作、字段、接口、异常分支，所以文档长度会明显大于普通 PRD。

当前写作口径

1. 主文档只覆盖 MVP 闭环。
2. 家长端、积分、广告、任务中心不进入当前主体。
3. 以当前前端真实页面和跳转逻辑为基础，查漏补缺，不凭空造流程。
4. 所有关键链路优先回答“用户点哪里、进哪里、填什么、调什么接口”。
