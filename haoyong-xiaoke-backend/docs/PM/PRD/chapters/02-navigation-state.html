02 导航与状态机

本章基于当前前端真实页面结构和路由守卫逻辑梳理产品导航与状态跳转。 当前问题不在于“没有页面”，而在于“已有页面如何按角色和状态正确承接用户”。

1. 当前页面结构

当前前端由主包 + 4 个业务分包组成，已经具备比较完整的页面骨架。 

主包
├─ 首页
├─ 课表
├─ 统计
├─ 我的
├─ 登录 / 注册 / 角色选择 / 角色信息
├─ 角色切换
└─ 通知 / 协议

子包
├─ 学员包：列表 / 详情 / 表单 / 家长绑定
├─ 教师包：教师列表 / 详情 / 薪资详情 / 考勤
├─ 课程包：班级 / 课包 / 课时 / 排课 / 请假
└─ 设置包：校区 / 子校区 / 发薪日 / 科目 / 通知 / 反馈

2. 当前导航入口

页面类型 当前入口 现状判断
主导航 TabBar：首页、课表、统计、我的 结构清晰，但未体现“首次进入必须完成的动作”
业务入口 首页金刚区进入学员、班级、教师、设置等页面 适合已完成初始化的用户，不适合首次进入的新用户
登录后导航 路由守卫中按登录状态与身份数量跳转 已具备基础，但当前仍缺少“机构未创建/教师未绑定”的状态细分

3. 当前登录后跳转逻辑

未登录用户
  -> 进入登录页

已登录用户
  -> 若存在 redirectPath，回原页面
  -> 若 identities.length === 0，进入注册流程
  -> 若 identities.length === 1，进入首页
  -> 若 identities.length > 1，进入角色切换页
当前问题：这套逻辑只解决了“有没有身份”，没有解决“身份是否已完成组织初始化”。这也是为什么 PRD 需要补上“机构/校区/绑定状态机”。

4. 建议状态机

下面这版是当前 MVP 更适合的状态机。它比现有逻辑更贴近真实业务，能减少用户进错页面。 

UNAUTHENTICATED
  -> 登录页

PRINCIPAL_NEED_PROFILE
  -> 角色选择页 / 校长机构信息页

PRINCIPAL_CREATING_ORG
  -> 创建机构 + 自动创建默认主校区

PRINCIPAL_READY
  -> 首页 / 教师邀请 / 学员管理 / 校区管理

TEACHER_UNBOUND
  -> 教师输入邀请码页

TEACHER_READY
  -> 首页 / 学员列表 / 课表 / 课时相关页面

PARENT_COMPAT
  -> 维持兼容，不作为当前重点
```mermaid
flowchart TD
    A[未登录] --> B[登录页]
    B --> C[微信一键登录]
    C --> D{是否已有身份}
    D -->|无| E[角色选择页]
    E --> F[选择校长]
    F --> G[校长机构信息页]
    G --> H[创建机构]
    H --> I[自动创建默认主校区]
    I --> J[首页]
    D -->|有校长身份| J
    D -->|有教师身份| K{是否已绑定校区}
    K -->|否| L[输入邀请码页]
    K -->|是| M[教师工作台]
    D -->|家长| N[兼容入口]
```

5. 页面入口建议

校长首次进入

先走最短注册闭环

校长首次登录后，应先完成“选校长 + 填机构名称”，随后自动建默认主校区，再进入首页。

教师首次进入

先完成绑定

教师登录后如果未绑定校区，应直接进入邀请码输入页，而不是直接落首页。

已初始化用户

再进入首页工作台

只有满足角色前置条件后，首页金刚区和工作台才有意义。

6. 本章结论

1. 当前前端页面结构已基本够用。
2. 现阶段最重要的不是加页面，而是加状态。
3. 后续 PRD 的重点不是重新发明导航，而是把“哪个角色在什么状态下应该进入哪个页面”讲清楚。
4. 下一章将进入校长主链路，重点梳理微信登录、身份选择、机构名称填写、默认主校区自动创建与首页放行。
